# Secure sessions and guided streaming workflows

## Authentication and privacy

The guest entry point is a light, branded login screen. Navigation and application APIs require an authenticated session. Registration and login return only `{"ok":true}`; profile information needed for the UI is fetched separately without email, password hash or session secrets.

Passwords use BCrypt. Email addresses and optional precise locations use AES-256-GCM with random nonces. Email lookup uses HMAC-SHA-256. Flyway V7 adds private columns; the startup runner encrypts existing email addresses and replaces the old plaintext column with an opaque per-user placeholder. Back up `DATA_ENCRYPTION_KEY` privately: changing or losing it makes stored fields unreadable. Do not commit it. Public content, including channel names and chat messages, remains intentionally visible to authorized application users.

The existing JWT implementation is retained on the server, encrypted inside a persistent HttpOnly cookie. The JWT and database session expire after seven days. `JWT_SECRET` must remain stable between deployments. Cookie flags are Secure on HTTPS, SameSite=Lax and Path=/api. The frontend stores no session token in Web Storage. The `/api` reverse proxy in Vercel and Vite keeps the cookie first-party; it must point to the intended Render backend. State-changing requests reject untrusted origins. Session-authenticated one-use connection tickets expire after 30 seconds and carry no profile payload; the backend consumes them for WebRTC signaling and relay connections and checks that their session remains active.

Browser developer tools can always inspect user-supplied input and data the browser needs to display. HTTPS protects transport; HttpOnly prevents scripts from reading the session cookie. Neither can hide a user's own input from their browser. These changes minimize response data and remove browser exception-object logging; they do not claim that every visible field is inaccessible to the device owner.

## Forms and interface

All sections use the light palette and descriptions. Shared form helpers enforce length, byte and numeric limits before API requests, while server validation stays authoritative. Registration accepts Gmail/Hotmail, validates the username, requires consent and shows password strength. Login and registration have a show/hide password button. Every async action has a busy button; foreground API requests have a shared activity indicator. Polls and background archive uploads remain quiet.

Channel creation starts empty. The URL slug is generated by the server; it is separate from physical location. A creator must explicitly enable location sharing and grant browser geolocation permission. Updates occur every 20 seconds. Exact location is shared only while recent (less than one minute); users can disable it in Settings. Location ciphertext is omitted from channel/dashboard API responses.

## Broadcast lifecycle and recordings

Navigating away from the studio preserves the outgoing MediaStream and recorder. A small in-app video appears with a return-to-studio button. Native Picture-in-Picture is offered only when supported. Opening another live stream during a broadcast uses an independent viewer connection, preserving the outgoing broadcast. Closing the browser or powering off the device ends capture; keeping a login session does not keep a camera running.

Independent 15-second recordings are uploaded to private storage and listed in the creator's profile. Ending a stream flushes the last part and waits for outstanding uploads. An abrupt shutdown can lose the current unsent part. Historical broadcasts before this feature keep their metadata; their missing video cannot be recreated. Replay follows the ordered parts and restricts access to the creator. The archive shares a configurable `ARCHIVE_BUDGET_BYTES` limit with existing media (default 200 MiB) to constrain database usage; this does not guarantee a provider's free quota or unlimited storage. On quota/network failure the live broadcast continues and the user is notified that recording stopped. Upload queues are bounded.

## Configuration and verification

Generate a 32-byte random base64 `DATA_ENCRYPTION_KEY` and a strong stable `JWT_SECRET` outside Git. In production, store them as private Render environment variables. Keep PostgreSQL under the private `streamguard` schema and the existing backend role. V7 enables RLS on the recording table and indexes its stream/asset relationships. The API's server role owns the new table; frontend clients have no direct database access.

Local verification on 2026-10-09: backend integration/unit tests, TypeScript strict compilation, localization checks, camera/lens tests and the new browser workflow test. Run `npm run test:workflows` with the backend and Vite running against a separate local database. It uses synthetic camera/microphone input and synthetic location coordinates, tests first-screen authentication, minimal responses, persistent HttpOnly cookies, WebRTC reception, floating preview, normal chat, profile recording replay, local numeric limits and mobile layout.
